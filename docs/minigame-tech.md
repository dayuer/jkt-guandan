# 二期小游戏：技术选型结论（#83）

> 2026-10-14，仓库所有者在会话里定下：**不使用引擎，全部原生开发**；同日定下**废弃语音开局（#122）**、**AI 对战（#88）和规则引擎（#87）推到三期以后**。本文是 #83 要求的选型结论，代码在 `app/minigame/`。

## 结论

| 项 | 选择 |
|---|---|
| 引擎 | **不用**。约局页面用小游戏原生的 Canvas 2D；三期以后的 AI 牌桌（#88）也一样，界面层自己写 |
| 语言与打包 | TypeScript，esbuild 打成单个 `game.js`（IIFE，目标 ES2017） |
| 仓库结构 | 本仓库 `app/minigame/`；和 H5 共用的纯逻辑直接 import `app/h5/src`；规则引擎（#87，和 #88 一起推到三期以后）到时放在共用位置，两端都能 import |
| 包体预算 | 主包 ≤ 4 MB。现在正式版 `game.js` 约 100 KB，开发者工具打包后约 140 KB；牌面素材以后走分包或 CDN |

## 为什么不用引擎

1. **最费事的部分引擎帮不上忙**。约局以表单和列表为主，小游戏里的文字输入只能用 `wx.showKeyboard`（屏幕底部的原生输入条），Cocos 的 EditBox 在小游戏里也是这个机制。引擎的 UI 系统在这一项上没有优势。
2. **包体和首屏**。不带引擎运行时，包体只有百 KB 级，在雅加达 4G 和工业园的弱网下首次加载最快。
3. **代码共用**。纯 TypeScript 模块直接 import，不经过编辑器和引擎的资源管线。H5 的状态提示、冲突处理、话术、学牌内容、实时客户端都已经直接复用，以后的规则引擎也一样。
4. **工作流**。不需要引擎编辑器，命令行就能构建、测试、预览，多个 agent 协作时没有二进制场景文件的合并问题。

## 原生方案怎么做（已经在 #85 里落地）

- **画布运行时** `src/core/app.ts`：
  - 场景栈和切换动画；
  - 每帧登记矩形热区；位移小于 8px、在 touchend 结束才算点按；
  - 带惯性和回弹的滚动，支持下拉刷新；
  - 底部弹层和居中对话框；toast；
  - 键盘：拉起原生输入条，画布上同步显示文字和光标，键盘弹起时弹层跟着上移；
  - 只在有变化或有动画时重绘。
- **常用控件** `src/core/widgets.ts`：导航栏（让开右上角胶囊）、按钮、胶囊、分段、输入框、列表、横幅、弹层模板。
- **必须由点按触发的接口**：订阅消息（#85、#137）要求在 touchend 里同步调用，热区的 `onTap` 正好在 `wx.onTouchEnd` 回调里同步执行，已验证。
- **不依赖 Intl**：安卓微信的 JS 引擎不保证带完整的 ICU，雅加达时间按固定 UTC+7 自己算（`src/lib/fmt.ts`）。
- **验证手段**：
  - 无界面端到端：在 Node 里模拟 wx 接口，HTTP 和 WebSocket 是真的，按热区 id 点按并截图；
  - 开发版 `--selftest`：在微信开发者工具的真实运行时里自动走一遍，回传报错和画布截图。

## 代价（需要接受的）

- **输入体验**：没有行内输入框。点字段后，在底部原生输入条里打字。
- **右上角胶囊**：设计稿里放在右上角的按钮要挪走。开局页的「取消」挪到左上，详情页的分享挪到底部操作栏，需要 design 出适配稿。
- **界面全部自己画**：
  - 文字折行、省略号、无障碍都要自己处理；
  - 读屏软件读不到画布内容，这是小游戏本身的限制。
- **字体**：用系统字体。衬线标题在没有宋体的安卓机上会退回无衬线；生僻符号改用 emoji 或路径绘制。

## 留给 #88（AI 牌桌，已推到三期以后）的要求

牌桌也用 Canvas 2D，不引入 WebGL 引擎。开工时先做一手 27 张牌的理牌、拖选和出牌动画的性能原型。这是 #83 原型里还没跑的一项。

- 预算：中端安卓机 60 fps，单帧绘制 ≤ 8 ms。
- 如果达不到，先做这几件优化，**仍然不换引擎**：
  - 牌面预渲染到离屏 canvas，绘制时只贴图；
  - 只重画变化的区域；
  - 动画只改位置和透明度。
